Forecasting a turbulence signal: recurrent networks, a Transformer, and the linear model that beats them

One velocity signal from a channel-flow simulation, extracted byte for byte from 106 files, cut into windows of 300 past values and the next 10. Recurrent networks halve the error of persistence and a small Transformer ties it, with three seeds deciding both verdicts. On exactly the same windows, a linear autoregressive model fitted in 42 milliseconds is 77 to 258 times better than every network, because ten steps of this signal are almost a straight line.

Objective

A probe in a simulation, a pressure tap on a wing or a sensor in a plant gives one signal in time, and forecasting a few steps ahead is the first thing a controller or a monitor needs. Recurrent networks and Transformers are the standard answer for sequences. I wanted to see what they actually buy on a real turbulence signal, the streamwise velocity at one height in a direct numerical simulation of channel flow, and to measure them against references that cost nothing to build. The work is four stages, each a notebook:

  1. Stage 1 — Extracting one near-wall velocity signal from 106 simulation files. A reusable loader reads 106 simulation files (5.64 GB), keeps one column of the velocity profile, and writes a 0.95 MB signal file that records which file every sample came from, so no training window straddles two files.
  2. Stage 2 — Forecasting the signal with recurrent networks. Windows of 300 past values and the next 10, split in time, scaled from training only; a dense network, SimpleRNN, GRU and LSTM against persistence (the last value repeated).
  3. Stage 3 — Forecasting the signal with a small Transformer. The same task for a two-block Transformer encoder that predicts all ten values, with sweeps of its size, horizon and input length, and recurrent networks with a ten-value head as references.
  4. Stage 4 — Horizon and baselines: what the networks buy over a linear model. Every network on exactly the same windows and test period, each predicting all ten steps, against persistence and a linear autoregressive model fitted by least squares, with the error at every future step.

Every training is repeated with seeds 0, 1 and 2, seed 0 being the base run, and I report the mean, the standard deviation and the range. A difference smaller than that spread is not an effect, and on this signal that rule changes more than one verdict.

Problem statement

Given the last 300 samples of the velocity at one wall-normal position (3 time units at a sampling step of 0.01), predict the next 10. Is a learned sequence model better than doing nothing clever? Which architecture, and does a difference survive a change of seed? And the question an engineer should ask before training anything: how far does a linear extrapolation of the past get on the same windows?

Method

One signal, cut so that nothing leaks

The loader is a class rather than a script, so that the signal is extracted once and the three later stages read the same file with the same windowing code. Two details of the split matter for honesty. The windows overlap (length 310, stride 10), so the first 30 windows after each cut reuse input samples from the block before it; no target is ever shared. And the scaling statistics (mean 0.9274, standard deviation 0.1015) come from the training inputs alone.

Two references that need no training

Persistence repeats the last observed value for all ten steps. The linear autoregressive model is one matrix: the 300 inputs and a constant, mapped to the 10 targets by least squares on the training windows, 3,010 coefficients solved in 42 ms. I also fit it on only the last L values, to see how much history a linear forecast needs.

The networks

Stage 2 trains with Adam at 1e-3 on the mean absolute error, early stopping after 8 epochs without improvement. Stage 3 trains with Adam at 1e-4 on the squared error, gradient clipping at norm 1, the rate halved after 4 flat epochs and at most 50 epochs. In Stage 4 every recurrent network gets a ten-value head and each family keeps its own stage's learning rate, so the comparison is of models as they were set up, not of a tuned optimum.

Which device

Each network is placed on its faster device with tf.device, rather than one device for a whole stage. One caution came out afterwards: for the same weights, the Apple GPU's GRU kernel gives a different output from Keras's reference GRU (my Stage 2 GRU scores 0.0530 with the GPU and 0.469 with it hidden, while the LSTM gives 0.0536 on both). The GRU results here therefore reproduce only on an Apple GPU, and the GRU timing compares two different computations.

Results 1 — The signal, exactly (Stage 1)

Running the extraction from the 106 raw files gave a file byte-identical to the one the later stages had been reading (SHA-1 f0a7789…): the stored signal equals the raw column to the last bit, and the 106 TFRecord shards it also writes read back identical.

Reading the files closely turned up three things worth knowing before training anything: the stored time vector restarts at 0 at the eighth file although the signal joins smoothly; the window loop yields 69 windows from the last file instead of 70; and the input overlap at the split cuts described above.

The GRU is lower than the LSTM in all three seeds, but by less than the LSTM's own spread, so I do not call it better. Two stacked GRUs reach 0.031, but they vary far more between seeds (0.024 to 0.039).

The dense network, on a flattened window with about 23,500 weights, gains almost nothing over persistence: the recurrent layers' state is what carries the trend.

These models end in one output, and Keras compares that one value with all ten targets, so each network predicts a constant across the window. Part of what looks like a weak network is a head that cannot express a trend; Stage 4 gives every network ten outputs.

The horizon sweep says the same in other words: a GRU trained for one step ahead reaches 0.0017 ± 0.0002, for 10 steps 0.0756 ± 0.0090 and for 50 steps 0.5912 ± 0.0059. In the sweeps, each capped at 40 epochs and scored at step 10, the window length is not monotonic (20 inputs 0.0694, 80 inputs 0.0528, 300 inputs 0.0756) and 8 units are too few (0.0860, against 0.0537 with 64).

Results 3 — The Transformer ties persistence (Stage 3)

In the base run the Transformer scores 0.0969 against persistence's 0.1028, and the notebook's verdict line says it wins; in my earlier run of the same notebook it scored 0.1045 and the verdict said persistence. Over three seeds it is 0.1017 ± 0.0047, so neither verdict is an effect.

The recurrent networks of the same stage reach 0.0363 to 0.0381, a third of the Transformer's error. That comparison mixes architecture with training settings (they train at 1e-3, the Transformer at 1e-4 for at most 50 epochs), so it says the Transformer as configured is the weak link, not that attention cannot forecast this signal. Its sweeps agree: a smaller model is worse (0.1164), a larger one no better (0.1025), and a shorter output is easier (one value 0.0312, twenty values 0.1941).

Every network is 77 to 258 times worse than one least-squares solve. With ten outputs the recurrent networks improve on their one-output versions (about 0.031 against 0.053) and still do not come close. The reason is the signal, not the networks: sampled every 0.01 time units, the near-wall velocity is smooth over ten samples, so a linear extrapolation is nearly exact, and the linear model needs only about ten past values to get within about a factor of three of its best.

Among the networks, SimpleRNN, GRU and LSTM do not differ by more than their spreads, and the Transformer at its stage's settings does not beat persistence. GPU training was repeatable for a given seed: the Transformer's seeds 1 and 2 in this stage reproduce Stage 3's runs to seven digits, which also means those two are not independent repeats of Stage 3.

Key observations

  1. Measure the reference that costs nothing first. On this signal a linear model fitted in 42 ms is 77 times better than the best network; persistence alone, the usual baseline, would have made the networks look good.
  2. Smooth at the sampling rate means linear at short horizons. Ten samples of a near-wall velocity at Δt = 0.01 are close to a straight line. Whether a network pays off at longer horizons, where linear extrapolation breaks down, is the question this setup cannot answer.
  3. Three seeds overturn single-run verdicts. The Transformer's "best method" flips between runs of the same notebook; over three seeds it ties persistence. The GRU-over-LSTM ordering holds in every seed but is smaller than the spread.
  4. The output head is part of the model. One output for ten targets predicts a constant; giving the same recurrent networks ten outputs, with Stage 4's training setup, drops their error from about 0.053 to 0.031.
  5. A comparison of architectures is also a comparison of settings. The Transformer trained at 1e-4 for 50 epochs is still improving when it stops; the recurrent networks it is compared with train at 1e-3.
  6. The fast device is not always the same computation. The Apple GPU's GRU kernel gives different outputs from the reference GRU for the same weights; a timing table without that check would have compared two different models.

Conclusion

The data path is exact: 5.64 GB of simulation output becomes a 0.95 MB signal, byte for byte reproducible, with every window inside one file and the scaling fitted on training data only. On that signal recurrent networks halve persistence and a small Transformer ties it, but a linear autoregressive model on the same windows beats all of them by two orders of magnitude, because ten steps of this signal are almost linear.

What the stages do not establish: the horizon stops at 10 steps (0.1 time units), so the regime where nonlinearity should matter is untested; the networks were not tuned (each kept its stage's learning rate and epoch cap); one wall-normal position of one simulation was used; and the GRU results are tied to the Apple GPU. The next steps are the horizon sweep extended until the linear model fails, a tuned Transformer at the recurrent networks' learning rate, the GRU retrained on the CPU, and a forecast of a quantity that is less smooth at its sampling rate, such as the wall shear stress.
